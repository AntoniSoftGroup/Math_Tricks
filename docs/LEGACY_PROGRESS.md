# Этап 4: совместимость старого прогресса

## Хранилище

В новый iOS-проект без изменения содержимого скопирован `Math_Tricks.xcdatamodeld`:
обе исторические версии модели и `.xccurrentversion`, выбирающий v2. Сохраняются
имена сущностей, optional-поля, Int16, Boolean и имя контейнера `Math_Tricks`.
Сгенерированные модели включаются в приложение как `Math_Tricks.momd`.

`LegacyProgressStorage.load()` получает URL из описания стандартного
`NSPersistentContainer(name: "Math_Tricks")`, как в старом AppDelegate.
Ни имя файла, ни каталог не подменяются новым именем приложения. Перед открытием
существующего SQLite проверяются метаданные и совместимость с включёнными моделями.
Если требуется переход с первой версии на v2, заранее проверяется возможность
inferred mapping и включается автоматическая lightweight migration Core Data.

Неизвестная модель, отдельные WAL/SHM без основного файла, старый маркер
инициализации без файла базы, ошибка копирования или ошибка чтения останавливают
загрузку. В интерфейсе есть повторная попытка. Удаления старой базы, очистки
UserDefaults, создания другой пустой базы вместо недоступной и принудительного
игнорирования версии модели нет.

На новой установке создаётся пустое совместимое хранилище. Предзагрузка каталога
и заполнение новых данных относятся к следующему слою данных. Чтение никогда
не запускает старый `Main.initDefaults()` или повторную предзагрузку приёмов.

## Резервная копия

Перед первым открытием существующего хранилища на запись `backup()` создаёт:

```text
Application Support/LegacyCompatibilityBackups/stage4-<store UUID>/
├── Math_Tricks.sqlite   # копия средствами Core Data с учётом SQLite-журнала
├── UserDefaults.plist   # исходный persistent domain, без значений по умолчанию
└── manifest.plist      # UUID, дата, метаданные и версия совместимости
```

Используется `NSPersistentStoreCoordinator.replacePersistentStore`, а не простое
копирование одного открытого SQLite-файла. Сначала файлы записываются во временный
каталог, проверяются `validateBackup()`, затем каталог публикуется переименованием.
Неполные временные копии не используются. Готовая копия не перезаписывается
при каждом запуске; проверяются её метаданные, UUID, манифест и plist настроек.
Ошибка существующей копии не приводит к её удалению или пропуску резервирования.

Это локальная копия перед совместимостью, а не пользовательский импорт/экспорт
или облачный бэкап из этапа 21. Автоматического восстановления поверх текущей базы
нет: исходные файлы и копия остаются доступными для отдельного восстановления.

## ID приёмов и уровни

`LegacyTrickMapping.json` содержит 107 уникальных пар старый ID → Android ID.
`LegacyTrickMapping.androidID(for:)` применяется только при чтении. Числа `id`
и `parent_id` в исходной базе не изменяются, записи не сливаются и не удаляются.

- 105 пар соответствуют одинаковым именам констант каталогов.
- `5016 → 17`: старый `trick_square_number_between_90_and_99_text()` возводит
  числа 90–99 в квадрат; Android `trick_square_number_between_11_and_99_text()`
  вопреки названию тоже генерирует числа около 100. У первых трёх уровней Android
  диапазон уже; исторические результаты сохраняются без пересчёта сложности.
- `7001 → 24`: `trick_2_root()` и `trick_square_root()` используют одинаковое
  построение полного квадрата из случайного числа и уровня с ответом-корнем.

Источники двух уточнений — `ios-legacy/.../BaseGame.swift` и
`android/.../player/Player.java`. Старые наблюдения о двух неразрешённых парах
в JSON-инвентаре этапа 1 остаются историческими; рабочая карта этапа 4 их разрешает.

`LegacySnapshotReader.read()` сохраняет для каждой строки исходный object URI,
старый ID, optional-поля, оценку, счёт и доступность. Неизвестные дополнительные ID
тоже сохраняются в снимке; их Android ID остаётся nil. Дубликаты не объединяются.

У обычных приёмов `id` уровня — номер 1–100, `parent_id` — старый ID приёма;
номер уровня сохраняется напрямую. У заучивания `parent_id` — множитель 1–100,
`id` — диапазон 1–10; множитель не преобразуется через карту приёмов.
Отсутствующие уровни и доступность новых уровней не выдумываются при чтении.

## Настройки, рекорды и единицы

`LegacyPreferences.init(domain:)` читает оригинальные ключи persistent domain:
монеты, решённые примеры, сложность, обычные/выбранные рекорды, длину партии,
победы игроков, звук, вибрацию, раскладку, цвет и `COREDATA_VERSION_OLD`.
Для отсутствующих значений используются только значения в памяти, например
500 монет новой установки. Сохранённые значения не перезаписываются fallback-ами.
Ошибочный тип значения не превращается молча в сброс пользовательского счётчика.

Числа читаются без сужения до Int16. `checked`, `status`, `status_fixed` и nil
остаются раздельными значениями. Неизвестные UserDefaults не очищаются и входят
в исходную резервную копию persistent domain.

Старые режимы 1–4 соответствуют Android MODE 0–3. Training=5 и byHeart=6 не
преобразуются в вымышленные Android MODE: там используются отдельные маршруты.
Ежедневная игра не наследует случайный старый рекорд.

Рекорды скорости в UserDefaults хранятся в **секундах**, в том числе дробных Float;
`Int.max` означает отсутствие рекорда. Они не читаются как целые очки или десятые.
Старые строки графика скорости (`id_game=3`) содержат **десятые секунды**;
`LegacyGraphProgress.speedSeconds` делит их на 10, сохраняя исходный score.
Дата графика хранится исходной строкой, без рискованного изменения часового пояса
или порядка одинаковых записей.

Маркер инициализации UserDefaults, версия модели Core Data и версия резервной
копии — разные значения; одно не записывается вместо другого.

## Подключение к приложению

Ниже описано подключение на этапе 4. После этапа 5 экраны работают через
`AppDataStore` и `ProgressRepository`, а совместимый снимок служит исходным
слоем данных; актуальная структура описана в [DATA_LAYER.md](DATA_LAYER.md).

- `LegacyProgressStorage` — actor, последовательно выполняющий дисковые операции.
  `newBackgroundContext().performAndWait` удерживает чтение на очереди Core Data;
  в UI возвращаются только immutable Sendable-снимки, не NSManagedObject.
- `LegacyProgressSession.prepare()` объединяет загрузку для нескольких окон.
- `AppRootViewController.loadProgress()` показывает загрузку/повтор, открывает
  навигацию только после получения снимка. Неверный прогресс не подменяется пустым.
- `AppRouter.start(progress:)` передаёт снимок временным разделам.
- Главное меню показывает прочитанные монеты и число решённых примеров. Полное
  оформление, просмотр уровней и изменения прогресса появятся на своих этапах.

Для выбора механизма использована документация Apple:
[автоматическая миграция](https://developer.apple.com/documentation/coredata/migrating-your-data-model-automatically),
[копирование хранилища](https://developer.apple.com/documentation/coredata/nspersistentstorecoordinator/replacepersistentstore(at:destinationoptions:withpersistentstorefrom:sourceoptions:type:)).

## Проверка

Компиляция успешна; обе модели и карта из 107 записей присутствуют в собранном
приложении. Исходные модели совпадают с legacy побайтно. Автотесты и создание
искусственных пользовательских баз не выполнялись. Фактический прогресс старой
установки и сценарии обновления проверяет пользователь на своих данных.

Debug-сборка с автоматической подписью установлена и запущена на iPhone 15 Pro Max.
Приложение перед установкой не удалялось. Лог: `/tmp/math_tricks_stage4_build.log`.
